Detection Telemetry Monitoring

An always-on early-warning system for detection telemetry volume. When a detection starts misbehaving in the field, the first symptom is usually a change in telemetry volume — this system catches it at the hourly level instead of waiting for someone to notice a bad week.

Role
Project owner — queries, scheduling, alerting
Status
Operational monitoring tool
Stack
Python · cloud data lake (SQL) · scheduled triggers · email

The Problem

Detection telemetry (signals describing how rules perform in the field) accumulates in a data lake. Volume anomalies — sudden spikes from a surging rule, or suspicious silence from a broken feed — carry urgent signals, but manually querying and eyeballing dashboards doesn't scale and doesn't wake anyone up.

The Solution

A layered monitoring system with three time horizons, each with its own query generator and monitor:

  • Hourly monitors — catch surges while they're still developing.
  • Daily monitors — day-over-day volume shifts and trend breaks.
  • Weekly monitors — slow drifts and week-over-week reporting for stakeholders.

Engineering Highlights

  • Programmatic data-lake querying — a query-builder layer generates the right SQL per time window, keeping the monitors DRY as new views were added.
  • Time-trigger orchestration — a scheduler component fires each monitor cadence independently, so an hourly failure never blocks the weekly report.
  • Automated email alerting — anomalies route directly to the stakeholders who own the affected detections, with the evidence embedded.
  • Iterative hardening — monitors went through revisions (hourly logic in particular) as real-world traffic patterns exposed edge cases; the current generation runs unattended.

What this project demonstrates: classic reliable automation — cloud data querying, scheduling, and notification design that turned a manual review chore into infrastructure the team trusts.
